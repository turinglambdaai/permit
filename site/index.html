THE MISSING PRODUCT LAYER

Payments are not permissions.

A payment event proves that money moved. An account proves identity. Neither gives an installed app a durable, portable answer to “what may this user run right now?”

Permit turns that answer into a signed artifact. The application verifies it locally with public keys it already trusts. A future management service may issue or refresh credentials, but authorization never depends on that service being reachable.

01

Exact bytes, no ambiguity

Ed25519 signs the decoded payload bytes exactly. Verifiers never parse and re-serialize JSON before checking the signature.

02

Rights outlive connectivity

Long-lived entitlements stand on their own. Products add short-lived activation leases only when their policy needs online control.

03

Policy without platform lock-in

Permit sits beside Rivet, Glaze, native apps, or any other runtime. The application framework never owns commercial policy.

permit — shell
$ raco pkg install --auto \
  --name permit https://github.com/turinglambdaai/permit.git

$ raco permit keygen \
  --key-id license-2026 \
  --issuer com.example

$ raco permit verify \
  --trust-store trust-store.json \
  --credential entitlement.permit.json

A DELIBERATE BOUNDARY

A protocol, not a billing company.

Permit v0.1 does not implement payments, accounts, pricing, tax, email, dashboards, hosted metering, or a license server. Future management systems may issue Permit credentials through this boundary; they do not belong in the verification core.
