THE MISSING PRODUCT LAYER

Payments are not permissions.

A payment event proves that money moved. An account proves identity. Neither gives an installed app a durable, portable answer to “what may this user run right now?”

Permit turns that answer into a signed artifact. The application verifies it locally with public keys it already trusts. Commerce or another explicit issuer service may issue or refresh credentials, but authorization never depends on that service being reachable.

01

Exact bytes, no ambiguity

Ed25519 signs the decoded payload bytes exactly. Verifiers never parse and re-serialize JSON before checking the signature.

02

Rights outlive connectivity

Long-lived entitlements stand on their own. Products add short-lived activation leases only when their policy needs online control.

03

Policy without platform lock-in

Permit sits beside Rivet, Glaze, native apps, or any other runtime. The application framework never owns commercial policy.

RACKET REFERENCE IMPLEMENTATION

From zero to verified.

Install the package, generate a key pair, sign a payload, then verify it with only the public trust store.

Browse source and test vectors →
permit — shell
$ raco pkg install --auto \
  --name permit https://github.com/turinglambdaai/permit.git

$ raco permit keygen \
  --private private-key.der \
  --public public-key.der \
  --trust-store trust-store.json \
  --key-id license-2026 \
  --issuer com.example

$ raco permit verify \
  --trust-store trust-store.json \
  --credential entitlement.permit.json

✓ verified entitlement

A DELIBERATE BOUNDARY

A protocol, not a billing company.

Permit v0.1 does not implement payments, accounts, pricing, tax, email, dashboards, hosted metering, or a license server. Commerce owns the family payment-to-rights workflow and may issue credentials through the explicit issuer boundary; it does not belong in the verification core.

Build one verifiable result.

先完成一个可验证的结果。

Compose Permit beside an application when signed, offline-verifiable rights are needed. Start with an entitlement and omit activation unless the product explicitly needs an online lease. Free products do not need a licensing subsystem.

需要签名且可离线验证的权益时，在应用旁组合 Permit。从 entitlement 开始；只有产品明确需要在线租约时才增加 activation。免费产品不需要授权子系统。

The Racket implementation requires the runtime and crypto dependencies declared by the package. Protocol v1 is implemented, but a stable 1.0 compatibility promise has not been declared. Independent verifiers must execute the normative vectors.

Racket 实现需要包声明的运行时与加密依赖。Protocol v1 已实现，但尚未宣布稳定 1.0 兼容承诺。独立验证器必须执行权威测试向量。

Keep issuer private keys server-side and public trust stores in clients. Verify first, then evaluate product/time/feature policy. Revisions replace snapshots the client has received; they do not revoke an offline credential immediately. Preserve backup/rotation paths for perpetual rights and separate entitlement keys from update/publisher keys.

签发私钥留在签发端，客户端仅持公钥信任库。先验签，再判断产品、时间和功能政策。revision 替换客户端已收到的快照，不会立即撤销离线凭据。为永久权益保留备份和轮换路径，权益密钥与更新、发行者密钥分离。
